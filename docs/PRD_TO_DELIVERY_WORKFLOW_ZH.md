## 2. 总体结论

### 2.1 明确判定

> **总体判定：当前形成的是成熟的“代码研发小闭环”，还不是完整、稳定的“PRD 到需求
> 交付大闭环”。**

这不是研发能力不足，而是流程在两个关键位置断开了：

1. **探索到立项的转换断点**：面对 Agent、RAG、SDK、自进化等不确定方向时，常在用户、
   问题、目标和验收标准尚未明确前进入实现，并迅速扩张为通用平台能力；
2. **代码完成到结果交付的转换断点**：测试和真实环境验证很强，但发布、迁移、采用、效果
   指标和反馈复盘没有成为统一的完成条件。

因此，当前研发方式可以直接概括为：

> **强工程、强实现、强技术验证；弱需求收敛、弱发布闭环、弱结果验证。已知问题交付稳定，
> 未知方向容易过早平台化。**

这份判断对应三个明确结论：

| 问题 | 结论 |
| --- | --- |
| 是否具备把明确需求做成可靠代码的能力？ | **具备，而且是当前最突出的优势。** |
| 是否已经具备稳定的 PRD 到交付流程？ | **尚未具备。流程依赖任务是否足够明确，而不是依赖统一门禁。** |
| 当前最高优先级是什么？ | **不是继续扩展 Core，而是建立“探索 → PRD → 最小交付 → 发布验证”的强制转换机制。** |

如果不改变，项目仍会持续产出高质量代码和丰富能力，但也会持续出现同一类结果：系统越来越
完整，真实交付边界却越来越难判断；测试全部通过，仍无法回答“谁已经在用、产生了什么结果、
是否值得继续扩展”。

### 2.2 判定依据：两种明显不同的研发模式

历史 session 中存在两种行为差异很大的模式。

| 维度 | 已知领域交付模式 | 探索型平台建设模式 |
| --- | --- | --- |
| 常见项目 | Fons、Nacos、Kubernetes、SQL 血缘修复、明确后端接口 | BI Agent、RAG、自进化、Base Agent、复杂 Flow |
| 任务起点 | 明确错误、字段、接口、状态或环境约束 | “还能做什么”“先看看方向”“做一个通用能力” |
| 需求表达 | 会指定只能改哪些列、哪些不能动、并发上限、异常状态和兼容要求 | 目标较宽，先参考多个项目，再让 Agent 提议下一能力 |
| 实施方式 | 先定位代码和原因，再做最小修改 | 设计、学习和实现交错，通过“继续”逐步扩张 |
| 验证方式 | 启动服务、跑真实 SQL、数据库、接口或集群验证 | 单元测试和 Starter 很强，但用户主路径验收出现得较晚 |
| 风险控制 | 关注影响面、旧环境不污染、配置化和回滚 | 技术上合理的能力容易在真实需求证明前进入 Core |
| 典型结果 | 改动边界清楚，可快速判断对错 | 系统能力丰富，但理解成本、公共 API 和返工成本增加 |

两种模式的差异说明：

> **你并不缺少需求交付能力；你缺少的是把探索结果切换成正式交付任务的强制转换步骤。**

当需求具体时，你已经会做范围控制、最小影响修改和真实验收。当方向不确定时，Session
容易同时承担产品经理、架构师、教师和实现者四种角色，Agent 的实现速度最终超过需求收敛
和自身理解速度。

### 2.3 分项成熟度判断

| 维度 | 当前表现 | 判断 |
| --- | --- | --- |
| 真实问题发现 | 大量工作来自实际 SQL、数据任务、服务、权限和集群问题 | 强 |
| 源码理解与诊断 | 会追问语义、复现错误、分析影响，并要求必要时先不改代码 | 强 |
| 架构与实现 | 擅长 Protocol、Adapter、状态、权限、恢复、测试和文档 | 强 |
| 技术正确性验证 | 同时使用确定性测试和真实数据库/服务/集群验证 | 强 |
| 已知任务范围控制 | 能明确禁止修改项、兼容边界和最小影响原则 | 强 |
| 探索任务需求收敛 | 容易从具体问题快速进入通用平台和未来能力建设 | 偏弱 |
| Plan 与 Implement 分离 | 多次出现方案刚形成就开始写代码，用户随后要求回到 Plan | 偏弱 |
| 用户验收 | 有真实下游测试，但没有普遍形成 PRD 验收与结果指标 | 中等 |
| 发布与反馈 | 缺少统一版本、Changelog、灰度、回滚和采用效果记录 | 弱 |
| 跨 Session 状态管理 | 已使用 docs 和 Claude memory，但主要记录技术事实，交付状态不足 | 中等 |

因此，当前更接近一名成熟的**架构与能力建设型研发**；下一阶段要稳定补齐的是**产品判断、
范围收敛和结果交付能力**。

### 2.4 根因：优化目标的优先级相反

当前自然倾向优化的是：

> 把能力设计得完整、通用、可靠，尽量覆盖未来可能遇到的问题。

PRD 到交付要求优先优化的是：

> 在明确用户、结果和约束的前提下，用最小范围尽快交付价值，再根据真实反馈决定是否扩展。

两者都正确，但顺序不能反。当前探索型 session 经常出现：

```text
真实问题或模糊方向
  → 阅读源码、论文和参考项目
  → 发现可以抽象成通用能力
  → Agent 提议下一步
  → 连续“开始 / 继续”推进
  → 技术体系快速变完整
  → 用户开始追问新增抽象和运行语义
  → 发现复杂度过高或偏离初衷
  → 补设计文档、重新收敛或新建重构版本
```

`base-agent` 从完整 Runtime、Worker、Recovery 和复杂 Flow，重新转向 `next/` 的 SDK 主
路径，就是这一矛盾的代表：旧实现并非技术质量差，而是实现了较多**技术上合理、但尚未被
核心用户路径证明必须存在**的能力。

### 2.5 如果不调整，会持续出现的后果

1. **返工从代码级上升到产品边界级**：需要重新判断哪些能力应该存在、放在哪里、是否暴露；
2. **理解债务累积**：Agent 实现速度超过自己理解新增抽象和运行语义的速度；
3. **完成边界模糊**：每完成一项能力，马上又进入“下一步还能做什么”；
4. **提交难以审查和回滚**：一个阶段同时跨越大量模块、文件和概念；
5. **Session 恢复成本高**：目标、决定、进度和阻塞点散落在长对话中；
6. **技术验证替代产品验证**：测试证明代码按设计工作，但不能证明用户需要全部设计；
7. **交付停在仓库内**：缺少发布、迁移、采用率和发布后效果证据。

### 2.6 唯一主线：从能力驱动转向结果驱动

需要从：

> **问题出现 → 尽量建设完整能力 → 测试技术正确性 → 再判断如何使用**

转变为：

> **确认用户问题 → 定义结果与验收 → 交付最小纵切 → 验证真实采用 → 再决定是否平台化**

这个转变不削弱已有架构、测试、文档和复盘能力，而是在它们前后增加三道门：

| 门禁 | 必须回答的问题 |
| --- | --- |
| 价值门 | 谁现在需要它？不做会损失什么？成功指标是什么？ |
| 范围门 | 本次最小交付是什么？明确不做什么？为什么现在必须进入 Core？ |
| 交付门 | 是否发布、被真实下游使用、可观测、可回滚，并验证了预期结果？ |

## 3. 研发习惯与流程画像

### 3.1 最值得保留的习惯

| 习惯 | Session 证据 | 价值 |
| --- | --- | --- |
| 真实问题驱动 | 工作集中在 SQL 血缘、RAG、Agent、权限、服务和 Kubernetes 等实际问题 | 技术投入与业务场景高度相关 |
| 先诊断再修复 | 多次明确要求“不要急着改代码”，先解释原因和影响范围 | 降低误修和生产风险 |
| 关注行为语义 | 会质疑 Gauge、Cancel、Plan、ToolCall、权限和状态迁移是否符合预期 | 能发现仅靠测试数量看不出的设计问题 |
| 明确最小影响边界 | 后端任务中会指定只能更新哪些列、其他列不能动、旧环境不能污染 | 已具备良好的变更控制意识 |
| 双重验证意识 | 既要求离线确定性测试，也坚持真实 SQL、Provider、数据库和集群测试 | 能兼顾回归速度和集成真实性 |
| 里程碑式推进 | Claude memory 记录过“一次一个 milestone，每步测试并 live verify”的节奏 | 在路线明确时能够形成稳定交付节拍 |
| 参考实现驱动 | 持续对比 AgentDemo、mock-manus、Hermes、OpenManus、PentAGI 等 | 善于吸收成熟模式而非闭门设计 |
| 文档与记忆沉淀 | 会要求保存设计、Review、TODO、测试流程、迁移说明和项目 memory | 有跨 Session 复用知识的意识 |
| 把重复操作自动化 | 将批量 audit、错误分类、最小修复和恢复机制逐步封装为 Skill/服务 | 能把一次性劳动转化为组织能力 |
| 保留 Git 提交控制 | 完整 Claude transcript 未发现直接 Git 写操作，常先查看 diff 再决定提交 | 正式变更边界相对谨慎 |

### 3.2 最需要纠正的习惯

| 习惯 | 表现 | 风险 |
| --- | --- | --- |
| 模糊方向直接进入实现 | “不知道还能做什么”后继续让 Agent 推进 | Agent 实际承担产品路线，技术合理性替代需求价值 |
| 抽象过早 | 单个场景很快上升为统一平台、通用 Core 或完整 SDK | 公共 API、维护和迁移成本提前发生 |
| “继续”缺少授权边界 | 115 条跨工具推进表达，大量依赖历史上下文 | 当前 Step 完成后，Agent可能自动增加下一能力 |
| Plan 与 Implement 混合 | 曾明确指出“Plan 才刚生成，怎么已经实现代码” | 方案未评审就形成代码和兼容负担 |
| 学习速度落后于实现速度 | 225 条概念/语义问题，部分发生在大量能力已经加入之后 | 出现理解债务，后期只能整体重构收敛 |
| 手工测试没有及时固化 | 经常要求按步骤手动测试，真实验收很强 | 同一行为需要重复验证，难以形成回归门禁 |
| 长任务依赖聊天监控 | 47 条进度询问，反复确认是否仍在运行 | 缺少独立 Run、心跳、阻塞原因和恢复入口 |
| 一个 Session 混入多个主题 | Agent 开发中插入 Shell、SQL、职业调研等，再返回原任务 | 上下文污染，约束和目标容易漂移 |
| 技术文档多，产品文档少 | memory 和 docs 能记录架构、Bug 和方向，但少有用户、指标、发布状态 | 知道“系统怎样工作”，不知道“需求是否已经交付” |
| 发布动作弱 | 355 条测试/运行表达，对比仅 12 条发布/交付表达 | 代码完成容易被当作需求完成 |
| 敏感信息进入 Session/Memory | 历史 transcript、Claude memory 和临时笔记中出现过凭据 | 日志、备份、分享和误提交都会扩大泄露面 |

### 3.3 已知领域任务的实际流程

```text
给出明确错误或改动点
  → 指定文件、函数、字段或环境
  → 说明不能修改的内容和兼容要求
  → 阅读实现并定位原因
  → 最小范围修改
  → 启动服务 / 执行 SQL / 请求接口 / 集群验证
  → 根据真实错误继续修正
  → 查看差异并决定是否提交
```

这条流程已经接近成熟交付方式。需要补的主要是：PRD/Issue 编号、自动化验收、发布记录和
结果反馈。

### 3.4 探索型任务的实际流程

```text
提出一个较宽的目标或询问还有什么方向
  → 阅读多个参考项目、论文和架构文档
  → 边学习概念边讨论设计
  → Agent 提出下一能力
  → 用户回复“开始 / 继续”
  → Agent 大量修改和测试
  → 用户再理解新增代码和抽象
  → 发现行为、复杂度或产品目标不一致
  → 补文档、切换方案或重新实现
```

真正需要改造的就是这条流程：探索可以开放，但探索结论在进入正式实现前必须重新形成 PRD、
验收标准、范围和停止条件。

### 3.5 长任务的实际流程

```text
启动批量 Audit / 修复 / 生成任务
  → Session 持续等待
  → 用户反复询问进度
  → 遇到不能修复的样本后人工要求跳过
  → 继续运行或从记录恢复
```

这类工作应该从聊天循环升级成独立任务系统，至少提供：

- Run ID；
- 当前阶段、总数、成功数、失败数和跳过数；
- 最近心跳和预计剩余时间；
- 当前阻塞原因；
- 可恢复游标和幂等策略；
- unresolved case 记录；
- 暂停、继续、取消和人工介入入口。

## 4. 从探索到 PRD 交付的目标流程

### 4.1 先判断任务类型

收到需求后，第一步不是写代码，而是选择路径：

| 类型 | 判断条件 | 允许产物 |
| --- | --- | --- |
| 标准交付 | 用户、问题、期望行为和系统边界已明确 | PRD、设计、代码、测试、发布 |
| Discovery Spike | 用户或方案不明确，需要验证可行性或价值 | 调研、实验、原型和结论文档，不承诺稳定 API |
| 诊断任务 | 已有系统异常，但根因和影响范围未知 | 复现和根因报告；未授权前不实施修复 |
| 运维任务 | 启动、迁移、批处理或恢复 | Runbook、执行记录、验证和回滚 |

探索型 Agent 项目最容易遗漏这一步。正确方式是先做 time-boxed Discovery Spike，得到明确
结论后结束 Spike，再创建新的正式交付任务，而不是在同一个 session 中自然滑入实现。

### 4.2 PRD 到交付九阶段

| 阶段 | 核心问题 | 必须产物 | 进入下一阶段的门禁 |
| --- | --- | --- | --- |
| 1. Intake | 谁提出了什么问题？ | Problem Brief | 有明确用户和问题，而不是只有功能名 |
| 2. Discovery | 是否值得解决？有哪些未知？ | 调研/Spike 结论 | 价值成立，关键未知已验证或显式接受 |
| 3. PRD | 本期交付什么结果？ | PRD、成功指标、非目标 | 验收标准可重复验证 |
| 4. Experience/API First | 用户怎样完成任务？ | 用户旅程、目标 API、CLI 或页面示例 | 主路径足够简单，消费者认可 |
| 5. Design | 最小技术方案是什么？ | RFC/ADR、风险和迁移计划 | 没有超出 PRD 的非必要能力 |
| 6. Slice Plan | 如何拆成可发布纵切？ | 任务列表和依赖 | 每个 Step 可独立测试、审查和回滚 |
| 7. Implement | 是否只实现当前纵切？ | 代码、局部测试、更新后的任务状态 | 不扩大范围，技术门禁通过 |
| 8. Accept & Deliver | 用户能否真实使用？ | 下游验收、版本、发布和回滚证据 | 产物已发布，不只是合并 |
| 9. Observe | 是否产生预期结果？ | 指标、问题和复盘 | 决定继续、调整或停止平台化 |

### 4.3 最小 PRD 模板

建议每项正式需求建立 `docs/prd/REQ-xxx.md`：

```markdown
# REQ-xxx：需求名称

## 基本信息

- Owner：
- 状态：Draft / Ready / In Progress / Released / Validated
- 目标版本：
- 关联 Issue / PR / Release：

## 用户与问题

- 目标用户是谁？
- 当前怎样完成任务？
- 当前成本、失败或风险是什么？
- 为什么现在必须解决？

## 目标与指标

- 用户最终能完成什么？
- 当前基线是什么？
- 用什么指标证明改善？

## 核心场景

1. 正常场景：
2. 异常场景：
3. 权限与安全场景：

## 范围

- 本期包含：
- 明确不包含：
- 后续候选项：

## 验收标准

- AC-01：Given ... When ... Then ...
- AC-02：Given ... When ... Then ...

## 风险与约束

- 兼容性：
- 安全与隐私：
- 性能和成本：
- 外部依赖：

## 发布与回滚

- 发布方式：
- 灰度范围：
- 回滚条件：
- 发布后观察指标：
```

对于 SDK，PRD 还必须先提供一段目标用户代码；对于服务，先提供请求/响应和操作路径；对于
数据任务，先提供输入样本、预期产物和质量规则。

### 4.4 Definition of Ready

需求进入实现前必须满足：

- 已明确真实用户和具体问题；
- 有成功指标或可观察结果；
- 核心场景和异常场景明确；
- 本期范围、非目标和停止条件明确；
- 有目标 API、页面、CLI 或数据产物示例；
- 权限、安全、兼容性和依赖风险已识别；
- 每条验收标准可指向未来证据；
- 已拆出第一个端到端最小纵切；
- Discovery 结论已经与正式实现分离。

对 Core 能力增加额外门禁：

> **没有真实消费者场景，不进入 Core；一个消费者不自动等于通用抽象。**

### 4.5 验收证据矩阵

每个需求维护下面的映射：

| 验收编号 | 用户可观察结果 | 实现位置 | 自动化测试 | 真实环境/下游证据 | 状态 |
| --- | --- | --- | --- | --- | --- |
| AC-01 | 待填写 | 待填写 | 待填写 | 待填写 | Pending |
| AC-02 | 待填写 | 待填写 | 待填写 | 待填写 | Pending |

测试通过只证明它覆盖的验收项，不得用一个局部测试声称整个需求已经交付。

### 4.6 双层测试策略

现有 session 对真实环境的坚持是优势，不应改成纯 Mock；但手工验证必须固化为回归。建议：

| 层级 | 目的 | 例子 | 执行频率 |
| --- | --- | --- | --- |
| 确定性回归 | 快速证明业务规则和边界 | FakeModel、内存 Store、固定 SQL fixture | 每次修改 |
| Adapter 契约 | 证明协议和错误映射 | Provider、PostgreSQL、Redis、HTTP fake | 每个 PR |
| 真实集成 | 发现环境、配置和依赖问题 | PostgreSQL、OneSQL、Kubernetes、真实 Provider | 合并前或 CI Matrix |
| 下游验收 | 证明用户主路径可用 | Starter、BI-WIKI、真实 CLI/API | 发布候选版本 |
| 发布后观测 | 证明结果与稳定性 | 成功率、耗时、采用率、错误分类 | 灰度和正式发布后 |

手工测试首次跑通后，应立即决定：

- 能否自动化；
- 不能自动化时，Runbook 放在哪里；
- 谁在什么时候重复执行；
- 证据怎样关联到验收标准。

### 4.7 Definition of Done

需求完成必须同时满足：

- PRD 每条验收标准都有可重复证据；
- 自动化测试、静态检查、构建和安装测试通过；
- 真实下游或 Starter 完成用户主路径验收；
- 权限、安全、兼容性和数据影响已经检查；
- 文档、示例、操作手册和实现一致；
- 版本号、Changelog 和迁移说明已更新；
- 产物已部署或发布到目标环境；
- 有灰度、回滚和观测方式；
- 发布后由明确 Owner 检查成功指标；
- 未完成项回到 Backlog，而不是隐含在“下一步”中。

## 5. AI Session 协作协议

### 5.1 六种工作模式

每个 session 开始时声明一种模式：

| Mode | Agent 可以做什么 | 退出条件 |
| --- | --- | --- |
| `LEARN` | 阅读源码、画调用链、解释概念 | 用户理解主路径，不修改代码 |
| `DIAGNOSE` | 复现、检查日志、定位根因和影响 | 有证据支持根因，未自动修复 |
| `DESIGN` | 写 PRD/RFC、比较方案、定义验收 | 用户选择方案，范围冻结 |
| `IMPLEMENT` | 只实现已批准的当前纵切 | 代码和局部测试完成，不扩大需求 |
| `VERIFY` | 执行回归、真实环境和下游验收 | 验收矩阵有可重复证据 |
| `DELIVER` | 更新版本、迁移、发布并进入观察 | 产物可用、可回滚、可观测 |

历史上已经出现过“Plan 才刚生成，为什么开始实现代码”的纠正。模式字段应成为明确授权，
而不是依赖 Agent 从上下文猜测。

### 5.2 Session 任务卡

每次开始工作，从 Issue 或项目内 `TASK_STATE.md` 读取：

```markdown
# REQ-xxx / TASK-xxx

- Mode：
- Goal：本次最终改善的用户结果
- Current state：已经完成并验证了什么
- This session：本次只交付什么
- Out of scope：本次明确不做什么
- Allowed actions：只读 / 文档 / 代码 / 提交 / 发布
- Done when：完成条件和命令
- Evidence：测试、日志、产物或下游验收位置
- Decisions：稳定决策及原因
- Next checkpoint：中断后从哪里恢复
```

Claude memory 已经能够保存架构方向、Bug 根因和里程碑，这是良好基础；需要新增的是 PRD
状态、验收证据、发布状态和下一恢复点，使 memory 从“技术知识库”变成“可交付状态”。

### 5.3 “继续”的固定语义

约定：

> **“继续”只表示继续任务卡中的当前 Step，不授权新增能力、扩大公共 API、切换架构目标
> 或自动进入下一个 Milestone。**

Agent 提议新增能力前必须回答：

1. 它对应哪条 PRD 验收标准；
2. 当前 Step 是否完成并有证据；
3. 为什么它是交付阻塞项，而不是“未来可能有用”；
4. 会影响哪些模块和下游；
5. 不做它是否仍能发布当前纵切。

### 5.4 一个 Session 一个主任务

- 新项目、新目标或非阻塞问题进入新 session；
- 临时 Shell/SQL 问题如果不阻塞当前验收，也单独处理；
- Session 结束时回写完成项、证据、未决问题和恢复点；
- 下一 session 读取项目状态，不依赖“你还记得上次做了什么吗”；
- 长 session 每完成一个纵切就结束，避免无限积累上下文。

### 5.5 长任务不由聊天充当进程管理器

Audit、批处理、生成和修复任务应提供独立 CLI/API/页面：

```text
run_id
status
current_stage
processed / total
succeeded / failed / skipped
last_heartbeat
blocked_reason
resume_cursor
started_at / updated_at
```

Agent 可以解释、处理异常和决定策略，但任务本身必须能在 Session 退出后继续运行、查询和
恢复。

## 6. Git、CI 与发布流程

### 6.1 提交和 PR 粒度

正式提交使用需求编号和稳定结果：

```text
feat(skills): REQ-017 discover trusted skill packages
fix(runtime): REQ-021 persist interrupted terminal state
docs(api): REQ-017 document skill package lifecycle
```

“感觉有问题”“建设中”“先测试看看”等过程信息适合放在 Spike、Issue 或 PR 描述中，不应
成为长期历史的唯一解释。

一个 PR 只交付一个用户可观察结果，并且能够：

- 独立解释价值；
- 独立测试；
- 独立审查；
- 独立回滚；
- 不要求审查者同时理解多套新抽象。

### 6.2 CI 门禁

以 `base-agent` 为例，建议统一覆盖：

```text
Root SDK
├── pytest
├── ruff
├── strict mypy
├── build
└── wheel install/import smoke test

Next SDK
├── pytest
├── ruff
├── strict mypy
└── public API / migration contract tests

Starter / downstream
├── offline end-to-end acceptance
├── package installation test
└── selected real integration tests

Repository
├── secret scanning
├── dependency/security scanning
└── documentation/link checks
```

根目录公布的命令必须与 CI 一致，并在干净 checkout 上可执行。手工命令笔记使用 Markdown
或明确忽略的 `scratch/`，不能破坏 `ruff check .`。

### 6.3 版本与发布

建立：

- `CHANGELOG.md`；
- SemVer 标签；
- Release Notes；
- wheel/sdist 构建和安装验证；
- 下游使用发布产物而不是仅使用 editable checkout 的验收；
- breaking change 的迁移说明；
- 灰度、回滚和发布后指标；
- 发布失败和下游不兼容的处理记录。

## 7. 对 `base-agent` / `next` 的具体落地建议

### 7.1 把 Skill Package 作为第一份正式 PRD

现有手工测试笔记已经包含很好的验收素材：

- 启用 Skill 后 instructions 进入最终 System Prompt；
- Skill 自带 Tool 自动可见；
- 未启用时 Tool 不可见；
- 缺少依赖或权限时在模型请求前失败；
- HarnessSnapshot 记录 Skill；
- Skill、ToolCall 和 Streaming 可以组合；
- Skill 不接触 Harness 内部类型。

下一步不是继续新增 Core 能力，而是：

1. 建立 `REQ-SKILL-PACKAGE.md`；
2. 把上述内容改写为 AC-01 至 AC-07；
3. 先在 Starter 自动化；
4. 使用真实 Provider 做发布候选验收；
5. 发布一个可安装版本；
6. 让至少一个真实下游项目使用并记录反馈。

### 7.2 给 `next` 明确退出条件

每项迁移记录：

- 对应 PRD、用户和下游场景；
- 旧能力保留、重写还是删除；
- 新旧行为差异；
- 自动化和下游验收证据；
- 兼容层或迁移步骤；
- 旧实现停止维护和删除条件。

整个 `next` 完成的条件是：

- SDK 主路径稳定；
- Starter 覆盖核心用户场景；
- 下游应用完成迁移试用；
- 公共 API 和迁移说明完整；
- 发布产物能够独立安装；
- 旧内核保留范围和删除时间明确。

### 7.3 暂停无 PRD 的 Core 扩张

在 Skill Package 完成一次完整发布闭环前，不再因为“以后可能需要”加入新的 Worker、并行
执行、复杂 Planner、动态 Tool Search 或生产基础设施抽象。真实需求仍可先在下游应用或
Spike 中验证。

## 8. 安全与隐私立即行动

审计发现敏感信息曾进入：

- 历史 Claude/Codex session；
- Claude 项目 memory；
- 当前工作树的手工测试笔记。

不在本文中复述具体值。建议立即：

1. 轮换仍有效的 API Key、数据库和客户端凭据；
2. 清理 `next/note.py` 等临时笔记中的明文密钥；
3. 检查并清理 Claude project memory 中的明文凭据；
4. Prompt、日志、文档和测试样例只保留脱敏占位符；
5. 本地 pre-commit 与 CI 同时运行 secret scanning；
6. 使用环境变量、短期 Token 或密钥管理系统；
7. 将 session 日志和备份纳入访问控制及保留策略。

## 9. 建议的 30 天落地顺序

### 第 1 周：建立边界

- 处理凭据轮换和 secret scanning；
- 创建 PRD、TASK_STATE、ADR 和 PR 模板；
- 约定六种 Session Mode 与“继续”的语义；
- 建立 root、`next`、Starter 的 CI 基线。

### 第 2 周：用真实需求试运行

- 选择 Skill Package 作为试点 PRD；
- 建立验收证据矩阵；
- 把手工验证转换为 Starter 自动化；
- 拆成可以独立审查和回滚的纵切。

### 第 3 周：完成一次真实发布

- 构建并安装发布候选包；
- 让一个真实下游项目使用；
- 补 Changelog、版本、迁移和回滚说明；
- 记录使用问题和采用成本。

### 第 4 周：复盘结果

- 检查验收标准和成功指标；
- 区分真实需求、未来候选和应删除能力；
- 决定 `next` 的下一迁移项；
- 统计本月新增 Core 能力中有多少来自已验证 PRD；
- 调整模板和门禁，而不是立即增加下一项平台能力。

## 10. 最核心的六条原则

1. **探索可以开放，但进入实现前必须重新形成 PRD。**
2. **没有真实消费者场景，不进入 Core。**
3. **“继续”只推进已选择的 Step，不授权 Agent 扩大路线。**
4. **一个 Session 一个主任务，权威状态保存在项目中。**
5. **每条验收标准必须指向可重复证据。**
6. **合并代码不是交付，发布并验证用户结果才是交付。**

最终的完成定义是：

```text
需求交付
= 明确的用户问题
+ 可验证的验收标准
+ 最小可发布纵切
+ 技术质量证据
+ 真实下游采用
+ 发布后的结果验证
```

最终结论：**你缺少的不是工程能力，而是把工程能力稳定转换为用户结果的交付机制。当前
最优先的工作不是继续扩展 Core，而是用一个真实需求跑通“探索、PRD、最小纵切、发布、
采用和结果验证”，并将这条路径固化为所有探索型任务的强制门禁。**
